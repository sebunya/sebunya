# Recommendation programme — decisions and dated assumptions

Each entry is dated. Assumptions are labelled ASSUMPTION and carry what would falsify them.

## 2026-08-06 — R0 reconciliation

- **D-R0-1 · One engine, evolved in place.** `GetRecommendationsUseCase` remains the only placement engine. The client-side selection engine in `apps/web/src/lib/recommendation-display.ts` (ladder + STALE_SLUGS + LOCAL_SEED_PRODUCTS) is scheduled for deprecation-with-proof: its truthfulness wins (slug safety, price/availability honesty, dedup by slug) migrate into the server contract; its catalogue veto and fabricated seed catalogue are removed. The product-finder quiz engine is out of scope and stays (recorded debt, not a duplicate placement path).
- **D-R0-2 · The catalogue content is the operator's.** The live 8 products are canonical truth for this programme. `LOCAL_SEED_PRODUCTS` is never rendered again: fabricated availability/prices violate the no-invented-facts rule. Replacing the demo-flavoured catalogue with the real GoldPlus range is a PIM import the operator runs/approves — carried on the open register, never blocking rails from truthfully recommending what exists.
- **D-R0-3 · Identity uses the owners that exist.** Opaque HttpOnly locator (`gp_visit`) → `experience_profiles` (token stored hashed, Postgres canonical). Event-stream stitching writes `identity_links` (the schema built for exactly this, currently writer-less). Canonical customer resolution stays with Customer DNA (`STABLE_ANONYMOUS_ID` is already an approved signal there). No new identity graph, no fingerprinting.
- **D-R0-4 · Same-origin relay replicates MEASURE-1.** Storefront events go browser → same-origin web endpoint → API, identity stamped server-side from the HttpOnly cookie. The public `POST /recommendations/events` stays compatible for already-cached pages; client-asserted `customerId` on that legacy path stops being trusted for identity metrics (recorded as untrusted-legacy in analytics).
- **D-R0-5 · Ops thresholds ship unset** (`recommendation_ops_config`, closed registry, payments discipline): exposure caps, cooldowns, curated-refresh windows. Ranking *penalties* (recently-seen/recently-recommended/post-purchase suppression) are deterministic policy components under `policy_version`, on by default — they are relevance behaviour, not business thresholds.
- **D-R0-6 · Honest tiny-data behaviour is the core requirement.** With 8 products, 0 paid orders, ~0 visitors: co-purchase/co-view/bestseller sources must report INSUFFICIENT_SAMPLE (never fabricate), copy must never claim personalisation or "trending" without evidence thresholds, and every rate below its minimum denominator reads "Not enough data yet".
- **D-R0-7 · Probe rows are marked.** Reconciliation wrote one live impression probe (anon `anon_r3probe0000001`, `metadata.probe=r3-reconciliation`). Any future synthetic rows carry the same metadata discipline so analytics can exclude them.
- ASSUMPTION-R0-A · The May 18–22 rail events were produced by real browsing of the then-working rails (placement mix ≠ seed script's list; seed script inserts rule IDs that don't exist in prod). Falsified if an operator confirms the demo seeder ran against prod that week; consequence either way: none — they are historic rows, preserved as-is.

Falsified/foldable if the driver pair is ever fixed repo-wide.
- **D-R9-4 · Popularity claims carry thresholds**: engagement TRENDING_MIN_SAMPLE=30 weighted units; bestseller BESTSELLER_MIN_UNITS_FOR_CLAIM=10 paid units. On release day the live engagement sample was 121 — the "Popular right now" title was evidence-backed at first paint.
- **D-R9-5 · Relay identity collapse is bounded, not eliminated.** Storefront beacons ride one server-side identity into the API; they get a dedicated `recommendations` rate-limit family (600/min) and the relay forwards X-Forwarded-For. ## 2026-08-07 — R3.1 commercial-intelligence closure

- **D-R31-1 · Attribution is a read-projection, one owner.** `DrizzleRecommendationCommercialRepository` recomputes order-item attribution from canonical truth on every read — idempotent, replayable and refund-reversible by construction. Model `last_eligible_touch_v1` (ATC 7d > click 7d; impressions = 1-day view-through assists only) rides in every payload; changing it silently is structurally impossible.
- **D-R31-2 · The identity join is the server profile, both sides.** Checkout now stamps `orders.profile_id` (+cart_id) from the HttpOnly visit token, SSR-forwarded — the 20 historic orders have no stamp and are classified UNATTRIBUTABLE forever, never inferred. No name/phone/time-proximity join exists.
- **D-R31-3 · COGS is frozen at sale time** (`order_items.cogs_snapshot_ugx` from `product_prices.cost_price`, 0102). Every cost_price is NULL today, so profit reports UNAVAILABLE/PARTIAL with the missing components NAMED — entering costs is the operator's (EXTERNAL_DATA_REQUIRED); the machinery activates from data alone. Partial refunds have no canonical line concept yet: full-order reversal via payment `reversed` is implemented; line-level refund allocation is UNSUPPORTED, named in-product.
- **D-R31-4 · ROAS gates on real spend.** `media_cost_facts` ships empty with server-only ingestion (recommendations.manage, logical-key dedupe). Until rows exist: UNAVAILABLE REASON=MEDIA_COST_NOT_CONNECTED. Incremental revenue stays UNAVAILABLE until a valid holdout experiment exists — attributed is never renamed incremental, and no configuration can override either rule.
- **D-R31-5 · JSONB is canonical at the writers.** Root cause found by driver probe: drizzle stringifies jsonb values AND postgres.js JSON-serializes jsonb params — two encodings. Writers now pass the RAW object/array through an SQL fragment with `::jsonb`, so exactly one serialization happens (real-PG round-trip proven). Readers keep tolerance for historic string rows.
- **D-R31-6 · The relay residual is CLOSED.** CADDY_EDGE trusts one forwarded hop and the R9 relay forwards the client address, so relay-carried events resolve their REAL visitor as TRUSTED at the abuse-control layer (unit-proven against resolveClientAddress). Safe because only in-network services reach the API port and Caddy rewrites external X-Forwarded-For.
- **D-R31-7 · CategoryPopularRail = EXTERNAL_DEPENDENCY.** No canonical category landing pages exist (`/shop?category=` filters one page, which IS the category listing). The rail stays wired-unmounted with its note; mounting waits for category pages, which this unit does not invent.
- **D-R31-8 · Browser proof runs on production, storefront scope.** Playwright (chromium desktop/mobile/tablet, `playwright.production.config.ts`) proves 18 read-only checks against the live release: rails truthful (populated charger PDP, honestly-empty mount PDP, 404 for fabricated slugs), signed HttpOnly locator invisible to scripts, no mock trackers, same-origin event capture, keyboard focus, structural a11y (landmarks/headings/skip-link/alt). ## 2026-08-07 — production closure

- **D-PC-1 · The refund ledger is the one refund truth (0103).** Refunds have always accepted a partial amount, but nothing recorded one: the only guard compared each request against the ORIGINAL collected amount, so two 60% refunds both passed and 120% of the money could leave, and a retry issued a second payout. `payment_refunds` (+ optional `payment_refund_lines`) now holds what was asked for, what it was allocated against, and what the provider did. The refundable balance is collected MINUS every non-rejected refund, computed under `SELECT … FOR UPDATE` on the attempt and reserved BEFORE the provider is called — proven on real PostgreSQL by two refunds racing for the same headroom, exactly one winning. A `requested` refund counts against the balance like a settled one: money in flight is not headroom.
- **D-PC-2 · A failed provider call keeps its reservation.** A timeout is not proof that no money moved, so the row stays `requested` and an operator reconciles it. A stuck reservation is recoverable; a double refund is not.
- **D-PC-3 · Partial refunds reduce a line, not an order.** Every commercial query used to drop an order outright when any attempt read `reversed` — an assumption ("full-refund reversal", D-R31-3) the partial path breaks, so a 5,000 UGX delivery-fee refund erased a 500,000 UGX order from revenue, margin and cohorts. Only a FULLY refunded order now leaves the paid set; anything less is subtracted from the line it was allocated against. A refund with no line allocation is order-level and reduces order totals WITHOUT inventing a per-product refund that never happened. Still exactly-once, because it is recomputed rather than applied. This supersedes D-R31-3's "line-level allocation UNSUPPORTED".
- **D-PC-4 · `.env.example` is force-scanned.** It is the one env file committed on purpose, so it is the one that must be scanned — it was skipped twice over (as a `.env` file, and as a non-allowlisted root config) while holding an administrative bootstrap password that hashed identically to production's. A `committed-env-secret` rule now fails on any non-placeholder value assigned to a secret-named key. The value survives in git history: rotation, not redaction, is the remedy.
- **D-PC-5 · A query that is only ever mocked is a query nobody has run.** `getTrendingEvents` grouped on `coalesce(recommendation_product_id, product_id)` but ordered by the bare `product_id`, which Postgres rejects — so the trending rung threw on every call, the engine logged `RECOMMENDATION_ENGINE_DEGRADED` and fell to NEW_ARRIVAL. It was invisible because serving never broke and every test for the method mocked the repository. Integration coverage now executes the SQL; `home_trending` serves POPULAR_NOW with real scores for the first time.
- **D-PC-6 · A dead image degrades to an honest placeholder.** Every catalogue photo 503s from its hotlinked source, and a broken-image glyph is the browser telling the customer the shop is broken. A delegated listener plus a sweep for `complete && naturalWidth === 0` (the listener alone misses images that failed before the deferred module ran) swaps in `/products/image-unavailable.svg`. Real product photography remains EXTERNAL_BUSINESS_DATA.
- **D-PC-7 · Admin sign-out happens on the server.** The button wrote `document.cookie` against an HttpOnly cookie, which browsers ignore, and never revoked server-side — an administrator who signed out on a shared machine had not. It is now a form POST to `/admin/logout` that revokes via `logout-all` and clears the cookie with `Set-Cookie`. Non-Astro files under the admin page directory are now explicitly classified rather than blanket-banned, so the guard still denies by default.
- ASSUMPTION-PC-A · The tablet project runs the iPad Mini VIEWPORT under chromium, because Playwright ships no WebKit for mac12-arm64 — that project had failed to launch on every run while the suite reported the checks that did pass. A real WebKit engine check needs a host that has one.
