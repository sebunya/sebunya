# Decisions

| ID | Decision | Alternatives | Source facts | Invariant kept | Trade-off / rollback |
|---|---|---|---|---|---|
| D-001 | Server-side ANALYTICS is always on (incl. GPC); browser analytics COOKIES follow the preference-centre choice | Dossier §3.5 consent-gated analytics | Owner decision 2026-09-19 (authority order puts owner first) | Honest disclosure: privacy #analytics, cookies page, preference copy say exactly this | Reversible by policy flag; recorded so reviewers don't "fix" it |
| D-002 | ADVERTISING sinks honour an EXPLICIT stored advertising refusal (preference centre) → SUPPRESSED(CONSENT_DENIED); no record = allowed | Suppress unless granted (dossier default) / ignore the toggle | Owner wants tracking on; the toggle exists and must not lie (CLAUDE.md: no dark patterns) | Withdrawal is re-checked immediately before dispatch | Owner can widen/narrow later |
| D-003 | Authoritative business events are appended INSIDE `OrderTransitionService.apply()` (the one transactional transition point), not in route handlers | Separate writer after commit (today) | Truth map: all status changes pass through apply(); order_events already idempotent by key | One source transition → one business event (unique environment+business_dedupe_key) | Event write failure rolls back the transition (dossier §4.3) |
| D-004 | `ad_destinations` (0138) is the destination config for ad sinks (MERGE), extended rather than a second `destination_config` table | New measurement.destination_config | Working admin, vault, tests already on ad_destinations | One config authority | Activation states beyond on/off added as columns when canary/test modes are built |
| D-005 | Kill switch HOLDS deliveries (RETRY_WAIT, reason KILL_SWITCH) instead of suppressing them | Suppress/cancel pending | A kill is usually temporary (bad payload, leak investigation); holding preserves eligible intent without sending | No network write while on | Operator can cancel explicitly |
| D-006 | COD `order_confirmed` (basis `approved_cod`) is emitted at placement, matching the owner's "a COD order is a sale when placed"; refused COD → `order_cancelled` → refund/withdraw | Wait for delivery | Owner semantics already in production GA4 purchase | Cancellation reverses unsent deliveries and refunds sent GA purchases | Revisit if COD refusal rate proves high |
| D-007 (SUPERSEDED by D-010) | Analytics stack (ClickHouse, PeerDB, Dagster, dlt, dbt, science runners) is NOT deployed on the commerce host | Co-locate with resource limits | Host 2 vCPU / 3 GB / 75 GB; dossier §1.3/§11.1 forbid contention | Checkout never starved by analytics | Blocked on a separate analytics host (B-001) |
| D-008 | Business-event writes run in a SAVEPOINT inside the commerce transaction; on failure only the event rolls back, the sale commits, and `measurement.write_failure` records it (alarm + repair list) | Strict atomicity (dossier §4.3: failed outbox insert rolls back the business transaction) | GoldPlus has never taken a paid order; a validation edge case must not be able to block payment settlement | Authoritative events are still written in the same transaction whenever they succeed | Strict mode is one flag away once the writer has production history |
| D-009 | Browser behavioural events keep the existing outbox → GA4/ads path; only SERVER commerce events (confirmation, cancellation) move to durable delivery intents | Route everything through intents now | Browser path verified in production 2026-09-19; the dossier ranks provider delivery of commercial outcomes first | Purchases/refunds get lease/attempt/unknown-outcome semantics | Browser events migrate with the collector contract (GP-WEB) |
| D-010 | Addendum 17 (2026-09-20): build a MEASURED, SCHEDULED single-host profile (commerce-core continuous; analytics-batch one bounded job at a time under a host-wide lease with resource admission; analytics-full kept as optional profiles). No component is claimed to fit until benchmarked | Separate analytics host (D-007) | Owner prefers the existing 2 vCPU / 3 GB host; ClickHouse documents ~2 GB low-ingest operation | Commerce is never starved: admission, aggregate cgroup budget, cancellation | Per-component verdicts FITS_MEASURED / FITS_WITH_SCHEDULED_MODE / NOT_YET_BENCHMARKED / EXCEEDS_AVAILABLE_BUDGET |
| D-011 | Attribution first runs on PostgreSQL (bounded, scheduled) over authoritative events, labelled observational; moves to ClickHouse marts when the batch profile is measured | Wait for ClickHouse | Addendum §3 (small incremental rule runs, weekly Markov/Shapley) | Same algorithms and fixtures either side | Postgres load is bounded by run caps |
| D-012 | `touchpoint.traffic_class` is set from the EDGE's own verdict (Cloudflare bot score < 60 → `automated`), only where Cloudflare is the edge; never inferred from the user agent in the handler | Leave the column at its default; or guess from the UA | An outright bot is already answered 204 by `botDetectionMiddleware`, so the handler only sees what got past it. A filter on a column nothing writes is a safeguard that looks real and is not (this was shipped and corrected the same day) | Attribution's `traffic_class = 'customer'` filter means something | If Cloudflare is not the edge the value is `customer`; a stronger classifier can replace the band without touching callers |
| D-013 | Journeys COLLAPSE consecutive same-channel touches, and the browser skips an identical touch signature within 30 minutes | Count every recorded touch | Opening a second tab from the address bar filed another `direct` touch and inflated direct. Dossier §9.2 allows consecutive-repeat collapse as a model option | Recorded `touchpoint` rows are never deleted or rewritten; the collapse is a model step declared in every run's `policy` | Turn off by dropping `collapseConsecutiveChannels` from the policy; the evidence is still there to recompute from |
